# Goal

Determine the evidence-backed path from the present DomainSpec-v2 state to its first production release, and preserve a durable strategy that can research new frontiers without confusing every newly discovered concern with a release blocker.

# TL;DR

DomainSpec-v2 is not ready for an unqualified production designation. Its first gate is G0: an external release owner must select the product lineage, supported actors, release form, profile, environment, claims, exclusions, compatibility boundary, support boundary, and accountable owners. The minimum-sufficient candidate is Option A, a private repository-local Validation Toolkit CLI. That candidate still needs authority reconciliation, a self-contained compiled runtime, fail-closed validation, recoverable state mutation, a bounded security and dependency boundary, operator documentation and support, enforced CI, clean release-candidate proof, and a controlled pilot before claim acceptance and release authorization.

This roadmap deliberately excludes UI, public distribution, a hosted service, a stable SDK, code generation, and Saturn/runtime convergence from Option A. Those are scope expansions, not unfinished hardening. The route is strict where omission could falsify the candidate contract or harm its actors and state, and deliberately stops where the evidence does not establish applicability. Coverage is complete only relative to this five-agent sweep and its sources as of 2026-07-12; it is not a universal production checklist. # Context

The dispatch was necessary because “make DomainSpec-v2 production” spans five evidence classes that cannot safely be collapsed: semantic authority, observed implementation behavior, dependency and constraint ordering, technical production controls, and product/operator readiness. The repository currently contains meaningful green tests and deterministic machinery, but it also contains an unresolved release contract, semantic count drift, fail-open validators, source-checkout coupling, unsafe multi-file writes, absent v2 CI, stale operator documentation, and dirty-snapshot evidence. Technical controls alone cannot establish operability, while documentation cannot repair false-green validation. [Agent 1](./research.md#agent-1--formal-authority-and-release-obligation-cartography), [Agent 2](./research.md#agent-2--empirical-runtime-and-executable-evidence-cartography), [Agent 4](./research.md#agent-4--technical-production-control-applicability-frontier), [Agent 5](./research.md#agent-5--operational-and-product-release-applicability-frontier)

The load-bearing repository boundary is explicit: the [Authority Model](../../../../projects/domainspec-v2/authority/AUTHORITY-MODEL.md) governs method, claim posture, source movement, and external release ownership; [DomainSpec-v2 definitions](../../../../projects/domainspec-v2/definitions/DEFINITIONS.md) govern canonical language; feature packs are primary specifications; implementation consumes and projects those objects; and the external implementation/platform owner decides implementation conformance and release. The roadmap is research synthesis. It does not ratify the candidate contract, promote definitions, mutate implementation, or self-authorize a release. ## Operational vocabulary

These meanings govern this roadmap only and remain candidate operational language:

- **Production status:** an external-release-owner decision that one named artifact/configuration is intended for sustained use by named actors inside a declared environment, compatibility boundary, and support boundary after claim-specific proof passes. It is not runtime correctness, general availability, or a version number.
- **First production release:** the earliest owner-approved release in the lineage selected at G0 that satisfies that production definition. It is not automatically the first DomainSpec-v2 tag or the full DomainSpec system.
- **Release:** owner-authorized identification and controlled availability of one exact source/artifact set, release identity, manifest/digest, contract, and evidence bundle. Immutable means the identified bits and records do not change; withdrawal or supersession adds new metadata.
- **Node-ready:** dependencies are closed, inputs are present, an execution owner is assigned, and no inbound block remains. **Release-ready** means every contract-required pre-release node and gate has passed.
- **Blocker:** a source, authority, witness, or boundary gap that stops a named move until it closes. G0 blocks branch-dependent implementation and any unqualified production designation, but not branch-invariant research or remediation.
- **Minimum-sufficient claim-protecting route:** all and only controls whose omission can violate a ratified obligation or credible failure mode inside the selected release contract.
- **Hardening:** increased robustness, safety, operability, or assurance for a capability already inside the contract, without expanding supported capability.
- **Scope expansion:** a product form or capability absent from the contract, including UI, public distribution, hosted service, SDK, code generation, or runtime convergence.
- **Applicable:** the selected contract, ratified policy, or credible in-boundary failure mode makes omission capable of falsifying a claim or harming a named actor or state.
- **Does not apply:** a necessary precondition is absent from the selected release form. The record must name the precondition that would reopen it.
- **Undetermined:** evidence or an owner decision is insufficient. Absence of evidence never establishes does-not-apply.
- **Frontier:** an unresolved observation, changed condition, or scope-expansion proposal whose applicability, owner, or remedy is unsettled against the current contract. Acceptance creates or changes a Craft node; the original record remains provenance.
- **Support boundary:** eligible users, versions, environments, capabilities, response posture, and exclusions. **Support mechanism:** channel, acknowledgement owner, triage, escalation, diagnostics handling, and end-of-support decision route.
- **Evidence:** a preserved source, observation, decision, or validation result with scope, provenance, version/environment, and time. **Proof:** the evidence package sufficient for one named claim under one named gate. **Receipt:** a stable reference to that package.
- **Deterministic:** for the same tool version, declared environment, supported input, and configuration, normalized outputs and verdicts are equivalent under the contract’s rule.
- **Build-time profile conformance:** a validator report that an input satisfies the profile ratified at R2. It does not imply semantic correctness, implementation behavior, runtime correctness, or convergence.

These repairs follow the authority boundary and the reviewers’ semantic attack: production cannot derive from SemVer, readiness must name its object, and completeness cannot exceed the five-agent evidence boundary. [Agent 1](./research.md#agent-1--formal-authority-and-release-obligation-cartography), [Agent 5](./research.md#agent-5--operational-and-product-release-applicability-frontier), [Semantic Versioning](https://semver.org/)

## Candidate Option-A contract

Until G0 and R2 ratify it, the candidate is:

> The named DomainSpec-v2 Validation Toolkit release is a private, repository-local CLI for authorized actors. Given an explicitly supplied feature-pack directory conforming to the profile ratified at R2, it reports build-time profile conformance, deterministically derives bounded obligations/specifications, performs declared negative/self-checks, and emits contained, versioned, recoverable artifacts with stable machine-readable results.

R2 must enumerate the profile; “backend” or “backend-core” is not a profile merely because the research uses the label. The candidate explicitly makes no semantic-correctness, implementation-conformance, runtime-convergence, agent-satisfies-spec, Saturn-actuation, code-generation, agent-cost, UI, stable-JavaScript-SDK, hosted-availability, public-availability, automatic-promotion, cryptographic-attestation, or broad-formal-proof claim. [Agent 1](./research.md#agent-1--formal-authority-and-release-obligation-cartography), [Agent 2](./research.md#agent-2--empirical-runtime-and-executable-evidence-cartography), [Agent 3](./research.md#agent-3--dependency-blocker-and-critical-path-cartography)

SemVer may be chosen for compatibility signaling. A 1.0.0 identity is coherent only if the owner intends to freeze the declared interface; a 0.y.z or non-SemVer identity can still receive production status if G0 explicitly accepts its instability. Production never derives from a major version. [Agent 5](./research.md#agent-5--operational-and-product-release-applicability-frontier), [Semantic Versioning](https://semver.org/)

Two migration gates remain separate:

- **RELEASE-SELF-CONTAINMENT** applies to Option A and blocks release: the selected CLI contract must have no runtime or proof dependency on v1 or unrelated sibling corpora.
- **V1-FREEZE** remains the existing owner gate in the [Import Manifest](../../../../projects/domainspec-v2/IMPORT-MANIFEST.md): every REFORMULATE row closes and build proof is green. Option A does not amend that criterion. V1 can remain unfrozen while a genuinely self-contained bounded toolkit releases unless G0 makes freeze a prerequisite.

## Persistent frontier operating protocol

The protocol uses existing Craft objects rather than a parallel registry. Its operating states are:

    observed → triaged
    triaged → researching | proposed | rejected | deferred
    researching → proposed | rejected | deferred
    proposed → accepted | rejected | deferred
    accepted → scheduled
    scheduled → verified
    verified → closed
    rejected | deferred | verified | closed → triaged on a reopen trigger

Severity is contract-relative:

- **S0:** current candidate/release contract can be falsified, private state exposed, or supported state corrupted. Triage immediately and block candidate/release movement.
- **S1:** credible material harm exists inside the contract without an active S0 witness. Triage before the next release gate.
- **S2:** bounded operability or quality issue exists inside the contract. Review during the next affected roadmap/release session.
- **S3:** advisory or scope-expansion proposal. It does not block release and is reviewed only on its trigger.

The Craft owner triages. The claim owner approves product-contract promotion; the semantic owner additionally approves meaning changes; the release authority approves changes to an authorized release boundary. Deduplication keys on affected contract clause plus normalized failure/observation signature. Duplicate evidence links to the existing gap; contradictory evidence remains a typed conflict.

Review is event-driven: immediately for S0; before G1 and G2; at release planning for S1/S2; when a reopen trigger fires; or when review_due_at expires. Evidence expires immediately when its source SHA, toolchain, environment, profile, or relevant implementation changes; operational receipts otherwise expire at the next release gate.

A frontier becomes a child research/experiment dispatch only when it blocks a node or materially changes applicability, a Principle-1 dispatch trigger holds, and a human confirms a tensioned sheet. Otherwise the owning capability or bounded task-session handles it. If no owner can be assigned, the node stays gated. If reproduction cannot be obtained, applicability stays undetermined. If proof cannot be produced, the move stays blocked or the claim narrows.
