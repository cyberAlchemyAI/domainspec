Cross-Tree Mirroring as a Coercion Mechanismfor LLM-Authored Code

Operator and Robot, working session 2026-05-18
vault/discovery/cross-tree-mirroring-for-llm-coercion
We propose a three-sibling top-level repository structure (/research, /domain_knowledge, /implementation) in which the two structured siblings share a feature-grammar so that for any artifact in one tree, the path of its counterpart in the other is computable rather than searchable. We distinguish two operations — promotion, taking residue into structure, and compilation, the categorical Δ taking L₁ into L₂ — with separate admissibility conditions. Adversarial review of the proposal forced the demotion of the strong "structure forces correctness" claim to "structure provides a computable spec lookup, enforced by a path-coherence validator," recoverable upon falsifiable measurement. Scope is narrowed to /domainspec and /maestro-trama.

§1Motivation

The originating engineering question of the framework is whether one can force a language model to write the right code. The categorical apparatus — the functor Δ : L₁ → L₂, the fractality predicates, the residue calculus — was developed afterward, as the apparatus by which "right" becomes checkable and "force" becomes mechanical.

The pilot repository maestro-trama exposes the failure mode the framework exists to prevent. An agent editing apps/labeling-platform/features/extraction/SPEC.md referenced ../../../../docs/features/... — a path that does not resolve. Fifty-plus broken cross-links of the same shape exist across the repository. The failure is structural: the agent had no computable path from its edit site to the spec that governs it.

§2Definitions and Structure

A sibling tree is a top-level directory in the repository. We propose three siblings: /research, /domain_knowledge, and /implementation.
The feature grammar is the path schema apps/X/features/Y/{aspect} shared between /domain_knowledge and /implementation. The sibling /research does not obey this grammar.
The two structured siblings form an isomorphism on objects at the (app, feature) level. That is, the function π : implementation → domain_knowledge defined by replacement of top-level prefix is a bijection on the set of paths obeying the feature grammar, modulo the multi-implementation case treated in §3.

§3Multi-Implementation

The strict bijection of Proposition 2.3 fails when a single specification is implemented by more than one application. In maestro-trama, the feature extraction is owned by the proposal ad-creative-dna (L₁) and instantiated by the application labeling-platform (L₂).

A spec is multi-implemented when its IMPLEMENTED-BY.md manifest names more than one path in /implementation/apps/. Each named implementation carries a reciprocal IMPLEMENTS.md pointing back to the spec.

Under this convention, specs are primary: code is an instance of a spec, not its peer. The functor Δ thereby admits one-to-many on objects.

§4Operations

A promotion is the operation taking a residue artifact to an L₁ artifact in place — an identity change without copy or compilation. Its admissibility conditions are:
  1. Necessary: the artifact has an earned (app, feature) identity.
  2. Sufficient: manual greenlight from the operator.

Partial identity (knowledge of app without feature, or feature without app) admits a relaxed form in which the artifact files under features/_unknown/ and promotes by frontmatter edit when the missing component earns itself.

A compilation is the application of the functor Δ : L₁ → L₂, generating a new artifact in the mirror tree. Its admissibility is gated by two conditions:
  1. The structural-completeness validator (§5) accepts the L₁ source.
  2. The test-derivation procedure produces tests deterministically (so the spec is not underspecified).
The T0' obligations of DomainSpec.lean — determinism, image-validity, entropy-bound — are the formal compilation admissibility conditions. They are deferred here as long-term aspiration; the structural validator suffices for the present discovery.

§5Validator

Let P denote the set of all file paths in the repository. The path-coherence validator is the predicate V : P → {accept, reject} defined by:

  1. V(p) = reject if p ∈ /implementation/apps/X/features/Y/ and there is no q ∈ /domain_knowledge/apps/X/features/Y/, unless IMPLEMENTS.md exists.
  2. V(p) = reject if p ∈ /domain_knowledge/apps/X/features/Y/SPEC.md and neither IMPLEMENTED-BY.md nor status: spec-only is declared.
  3. V(p) = reject if p ∉ /research/ and p does not parse as a tuple (layer, app, feature, aspect).

The validator is implemented as a pre-commit hook and CI gate. This is the enforcement layer; the coercion claim is recoverable only after measurement (see §6).

§6Open Question — Falsifiability of the Coercion Claim

The discovery does not claim that structural symmetry forces LLM correctness. That claim is held in reserve, pending a measurement protocol. The candidate protocol instruments N model-authored edits in maestro-trama pre- and post-migration, measuring the rate of broken cross-references and the rate of spec-divergent code. Should the structural mirror fail to move these rates, the warrant collapses and the proposal reduces to a navigation aid.
